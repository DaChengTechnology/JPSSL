# 自测通过不算数：jpssl 的测试方法、基准对比与互通实战

上一篇聊了 jpssl 的吞吐量怎么抠出来（AES-GCM 解密约 7 GB/s、Base64 21 GB/s 那些数字），评论区最常被问到的问题其实是另一个：**数字是真的吗？正确性怎么保证？**

这个问题比性能更本质。密码学库有个经典陷阱：**自洽性不等于正确性**。两端都用同一套实现，握手能通、数据能解，不代表你实现了标准——只要两端犯同样的错，一切都会"看起来正常"。jpssl 就真踩过这种坑：ClientHello 的 key_share 一度漏掉 2 字节向量长度前缀，自家客户端和自家服务端互测全绿，但任何标准 TLS 1.3 实现都会直接拒绝。

所以这篇不聊性能，聊方法论：jpssl 怎么测（测试方法）、怎么和 OpenSSL 同台对比（对比方法）、怎么和"别人家的实现"真握手（互通操作）。所有内容都来自仓库里现成的测试代码和输出，文末给复现命令。

## 一、测试方法：三层防线

### 第一层：RFC 标准向量，先把"标准答案"钉死

算法类测试第一件事就是和 RFC 官方向量对答案，不允许自造"参考答案"：

- **AES / GCM / CCM**：NIST 向量，覆盖单块、ECB、CBC、GCM（软件 / auto / AVX2 / AVX512 各路径）、CCM，AES-128/192/256 全密钥长度，`test_aes_modes` 共 1236 项断言；
- **SHA-1**：NIST/FIPS 向量、100 万个 'a'、边界长度 0/55/56/57/63/64/65/119–129、增量与逐字节更新；
- **Ed25519 / Ed448**：RFC 8032 向量；**X25519 / X448**：RFC 7748 向量；
- **Base64**：RFC 4648 向量 + 全长度随机往返 + 非法输入，484 项断言；
- **QUIC**：RFC 9001 A.1 / RFC 9369 A.1 的 Initial 密钥、A.5 的 1-RTT 密钥与头部保护掩码，全部逐字节匹配。

向量能抓住"算错了"，但抓不住"算的方式和标准不一致"。所以有第二层。

### 第二层：拿 OpenSSL 当"参考预言机"，交叉验证

OpenSSL 是世界上被验证最多的 TLS 与密码学实现，用它做交叉验证最便宜也最有说服力：

- 同一份随机输入、同一把密钥，要求 jpssl 与 OpenSSL 的输出**逐字节一致**——密文、认证标签、哈希、签名全部比对；
- **篡改检测**：把密文或标签任意改一个字节，必须解密失败（`test_aes_modes`、`test_dtls` 都覆盖）；
- **SIMD 多路径交叉验证**：AVX2、AVX-512、NEON、标量多套实现算同一个输入，结果必须一致——防止"加速路径优化出了 bug"；
- **SM2 双向签名互通**：OpenSSL 验 jpssl 的签名，jpssl 验 OpenSSL 的签名；
- `test_openssl_compare` 做综合比对，`test_x25519_ossl`、`test_ecdsa`、`test_sm`、`test_rsa_pss`、`test_sha1/3/512` 各覆盖一块。

### 第三层：协议级端到端 + 边界 + 稳压

算法对了，协议层还有一堆容易翻车的地方：半包粘包、消息分片重组、乱序重传、会话恢复、证书链。第三层专门打这些：

- **`test_tls`**：TLS 1.2/1.3 单元测试，累计 136 条断言，含线级 RFC 8446 上下文校验、"未广告的方案必须拒绝"等负面测试；
- **`test_dtls`**：54 项——内存数据报握手、cookie 交换、分片/重传、篡改拒绝、UDP socket 端到端；
- **`test_quic`**：86 项——v1/v2 × AES-GCM/ChaCha20 完整握手往返，客户端与服务端派生的数据包保护密钥逐字节一致；
- **`test_tls_socket`**：79 项——外部 fd 托管、借用模式、UDP 数据报模式、40000 字节大消息跨数据报自动合并；
- **`test_tls_large_msg`**：专打边界——16 KiB 记录边界、64 KiB 长度字段边界、256 KiB 大消息、TLS 1.2、socket 端到端 128 KiB 单次 send/recv；
- **`test_tls_stability`**：稳压测试，默认约 10 秒一轮（适合 CI），也能拉到 **2000 轮 TLS 1.3 + 4 个并发 worker × 每 worker 100 轮 socket 握手**，覆盖 Ed25519 / ECDSA P-256 / RSA-2048 证书轮换、0-RTT / PSK 会话恢复，统计各阶段耗时、失败次数与进程内存增长（泄漏启发式，阈值 `--leak-mb` 可调）；
- 对 X25519 / Ed448 这类最容易出错的域运算，仓库还配套分步诊断工具（`diag_ge`、`verify_ladder_steps.py` 等），逐层导出中间态与独立脚本模拟比对。

### 防线之外：CI 全平台跑

GitHub Actions 共 7 个工作流（另有 GitLab CI）：Linux x86_64、ARM64 Linux 跑全量 `ctest`；Windows MSVC 跑 `ctest`（OpenSSL 可选，找不到时对比测试自动跳过）；iOS / macOS / Android / 鸿蒙做构建 + 产物校验（XCFramework、AAR、`libjpssl_cpu.a/.so`、lipo/codesign）。

一个细节：基准程序在 CI 里**只编译不运行**——CI 负载下的计时波动会让基准偶发失败，所以基准交给本地跑，测试则全量跑。

## 二、对比方法：性能数字怎么测才不算"吹"

先声明一个前提：jpssl 库本身**零依赖**，OpenSSL 只出现在测试和基准里当参照物。和 OpenSSL 同台对比，最容易被质疑的就是口径，我们的做法如下：

**1. 同机、同 Release、同一份数据。** jpssl 与 OpenSSL 在同一台机器、同一编译器配置下测，密钥、IV、明文由同一个 `RAND_bytes` 生成。

**2. 先验正确，再计时。** 每个基准段开头先做正确性交叉验证——密文和认证标签必须与 OpenSSL 逐字节一致，通过了才进入计时。杜绝"测了个错误实现还跑得飞快"。

**3. 缓冲预分配，计时区间无堆分配。** jpssl 和 OpenSSL 的输出缓冲都提前分配好，`std::vector` 扩容不计入时间。

**4. 预热 + 自适应迭代 + 多轮取最小。** 先预热（含首次 CPUID / 缓存），按每轮约 200ms 自适应迭代次数，跑 5 轮取最小值，消除 CPU 频率波动与首次调用开销；`--target-ms`、`--rounds`、`--data-mb` 都可调。

**5. 场景口径对 OpenSSL 只严不松。** 这是最重要的一点：`bench_cipher_suites` 里 jpssl 按 **16 KiB TLS 记录分片加密、逐记录派生 nonce（base_iv ^ seq）**——这是真实 TLS 记录层的工作方式；而 OpenSSL 用 EVP 一次性整块调用（单 IV，最理想的情况）。也就是说对比没给 jpssl 减负，jpssl 反而额外背着分片与 nonce 派生的开销；`--record 0` 可退化为整块吞吐，方便单独比算法。

**6. 持平也如实写。** 结果不是单方面"碾压"：SM3 与 OpenSSL 持平，部分 CCM 场景持平。确实反超的是这些（i7-13700K / MSVC Release 实测，来自 README 与 CHANGELOG）：

| 项目 | 结果 |
|---|---|
| AES-128-GCM 解密（16 KiB 记录） | 约 7 GB/s，反超约 1.6× |
| AES-256-GCM 解密 | 约 3.9 GB/s，反超约 1.3× |
| TLS 1.3 记录层加密 | 约 1.7 GB/s，单条 16 KiB 记录 0.7–1.1 µs |
| Base64 编码 / 解码 | 21–22 / 17 GB/s（标量仅 3 / 0.2 GB/s） |
| SM2 keygen / sign / verify | 反超 1.31× / 1.35× / 1.26× |
| Ed448 keygen / sign / verify | 5.7× / 6× / 2.3× |
| Ed25519 批量验签 | 256 条 10.5–12 ms，约 2.3–2.6× |
| SM4 ECB / GCM | 反超约 1.2–1.3× |
| X25519 ECDH | 约 39.6 µs/op，约 1.15× |
| RSA CRT 解密 | 半尺寸汇编 + OpenMP 双线程，相对自身串行提速 1.5–1.7× |

复现很容易，README 里所有数字都能跑出来：

```bash
git clone https://github.com/DaChengTechnology/JPSSL.git && cd JPSSL
cmake -S . -B build-bench -DCMAKE_BUILD_TYPE=Release -DJP_ENABLE_BENCH=ON
cmake --build build-bench
./build-bench/benchmarks/bench_cipher_suites --data-mb 32 --record 16384 --rounds 5
./build-bench/benchmarks/bench_base64
./build-bench/benchmarks/bench_sm_ossl
```

## 三、互通操作：和"别人家的实现"真握手

自测 + 交叉验证能保证"算得对"，但协议栈的最终裁判是**与独立实现互通**。jpssl 的互通测试全部是进程内真实 socket 双向握手，每个用例断言三件事：握手成功、协商出的套件与目标一致、双向应用数据一致。

### TLS 1.2 / 1.3 ↔ OpenSSL 4.0

- **TLS 1.2**：25 个套件 × 2 方向（jpssl 服务端 ↔ OpenSSL 客户端、OpenSSL 服务端 ↔ jpssl 客户端），共 **50 个用例全部与 OpenSSL 4.0 互通**，覆盖 ECDHE-ECDSA / ECDHE-RSA / RSA / DHE-RSA / PSK / DHE-PSK × GCM / ChaCha20-Poly1305 / AES-CBC。
- **TLS 1.3**：AES-128/256-GCM、ChaCha20-Poly1305、AES-128-CCM，以及国密 RFC 8998 的 TLS_SM4_GCM_SM3 / TLS_SM4_CCM_SM3（OpenSSL ≥ 4.0 才参与，否则编译期 SKIP）。一个例外如实说明：AES-128-CCM-8 目前被屏蔽，因为 OpenSSL 4.0 对 CCM-8 握手直接报 "no ciphers available"——是 OpenSSL 侧不支持，不是 jpssl 的问题，但测试里明确标出来，而不是假装全过。
- 还有一个"替对端排雷"的细节：OpenSSL 3.x 默认不把 ffdhe 命名组用于 TLS 1.2，所以互操作测试里给 OpenSSL 服务端显式生成 ffdhe2048 参数，DHE 套件才能互通——写互通测试本来就要懂对端的行为。

### DTLS 1.2 / 1.3 ↔ OpenSSL / wolfSSL

- **DTLS 1.2 ↔ OpenSSL 4.0**：ECDHE-ECDSA × AES-128-GCM / ChaCha20-Poly1305 双向互通。
- **DTLS 1.2 / 1.3 ↔ wolfSSL 5.9.2**：重头戏，4 套件 × 2 方向 = **8 个用例全部通过**——DTLS 1.2（ECDHE-ECDSA-AES128-GCM-SHA256、ECDHE-ECDSA-CHACHA20-POLY1305-SHA256）、DTLS 1.3（TLS_AES_128_GCM_SHA256、TLS_CHACHA20_POLY1305_SHA256）；每个方向还做证书链双向校验（wolfSSL 验 jpssl 的链、jpssl 验 wolfSSL 的链）。调试时 `WOLF_CASE=<0..7>` 可以只跑单个用例，方便逐用例抓包定位。
- **DTLS 1.3 ↔ OpenSSL**：OpenSSL 目前没有实现 DTLS 1.3，测试用编译期探测自动 SKIP，上游一旦支持，真实互通用例会自动启用。

### QUIC v1 / v2 ↔ OpenSSL QUIC + 独立解析器

- **QUIC v1 ↔ OpenSSL QUIC**：双向互通（jpssl 客户端 → OpenSSL QUIC 服务器、OpenSSL QUIC 客户端 → jpssl 服务器）。测试内置一个最小 RFC 9000 报文层：长包头 Initial/Handshake、短包头 1-RTT、RFC 9001 §5.3 的 AEAD（nonce = IV ⊕ pn）、§5.4 头部保护、CRYPTO / ACK / STREAM / PADDING / HANDSHAKE_DONE / CONNECTION_CLOSE 帧。
- **QUIC v2**：OpenSSL 4.0 只支持 v1，所以测试验证的是 v2 Initial 能正确触发 RFC 9000 §6.1 的版本协商（版本协商包只列 v1），然后客户端按规范回退 v1 完成握手与数据传输。
- **线格式合规**：jpssl 生成的 v1/v2 Initial 包，交给**独立实现的 Rust quic-parser**（canmi21/quic-parser）解析、去除头部保护、AEAD 解密、重组 CRYPTO 帧，必须还原出合法 ClientHello；这个校验工具本身还用 RFC 9001 Appendix A.2 的官方 1200 字节向量做自检，防止"校验器自己也是错的"。

### 互通测试到底抓出过什么 bug？

这是最有说服力的部分——下面这些问题，全部是自家回环测试发现不了、由互通测试暴露的：

1. **ClientHello key_share 缺 2 字节向量长度前缀**（RFC 8446 §4.2.8）——两端自洽但不符合标准，标准实现直接拒绝；
2. **X.509 v3 证书被编码成 v2**——version 字段语义错误，与 OpenSSL 互操作时证书版本降级；
3. **DTLS 1.2 客户端固定默认曲线**生成 ECDHE 密钥对，服务器选 P-256 时发出 Y 坐标全零的非法点，被 wolfSSL 实测拒绝（改为按 ServerKeyExchange 选择的曲线重新生成）；
4. **DTLS 1.2 服务器证书链跨数据报丢失**——RFC 6347 允许每条握手消息独立数据报，需要持久化已解析的证书链；
5. **DTLS 1.3 一连串合规细节**：P-256 key_share 必须是 65 字节未压缩点（0x04‖X‖Y）、ServerHello 的 supported_versions 必须是单值、密钥调度缺 Derive-Secret(Early Secret, "derived", "")、CertificateVerify 签名内容必须是 64×0x20‖context‖0x00‖transcript_hash、Finished 密钥要从 handshake traffic secret 派生；
6. **ECDSA / SM2 证书签名必须是 DER 编码的 ECDSA-Sig-Value**——raw r‖s 格式会被 wolfSSL 严格拒绝；
7. **记录解密的最小密文长度检查过严**——wolfSSL 不把明文填充到 16 字节，需要放宽。

这些修复都进了 CHANGELOG 1.1.0。如果没有互通测试，第 1、2、5 条会一直藏在"自家两端一切正常"的假象里——这正是文章标题说的"自测通过不算数"。

## 结尾：全部可以自己复现

测试、对比、互通三件事，仓库里都有现成命令：

```bash
# 全量测试（含 OpenSSL 交叉验证与互通）
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure

# 稳压测试
./build/tests/test_tls_stability --iters 2000 --socket-iters 100 --threads 4

# wolfSSL DTLS 互通（先按 wiki/Testing.md 构建 wolfSSL 5.9.2）
cmake -S . -B build -DJP_WOLFSSL_PREFIX=$PWD/wolfssl-install -DJP_WOLFSSL_CERT_DIR=$PWD/wolfssl-src/certs
./build/tests/test_dtls_wolfssl_interop
```

jpssl 是 C++20 零依赖的跨平台密码学库（TLS 1.2/1.3、DTLS 1.2/1.3、QUIC v1/v2、国密 SM2/SM3/SM4，覆盖 Windows / Linux / macOS / Android / iOS / 鸿蒙）。所有测试、基准、互通用例都在仓库里：[https://github.com/DaChengTechnology/JPSSL](https://github.com/DaChengTechnology/JPSSL)

如果跑出和你预期不符的数字，或者某个用例在你机器上失败，欢迎提 Issue——上面的 bug 列表就是这么来的。觉得有用，也欢迎给个 Star。
