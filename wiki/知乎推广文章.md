# 把吞吐量抠到极限：这个 C++20 密码学库，AES-GCM 解密 7 GB/s、Base64 21 GB/s

做密码学库，正确性只是及格线，**吞吐量才是分水岭**。

同样的 AES-GCM，不同实现之间能差出两个数量级。我自己在写 jpssl 的过程中就踩过这个坑：一开始 AES-128-GCM 只有 0.012 GB/s——逐位软件乘法算 GHASH，基本不可用。一路优化到现在，**解密稳定跑到约 7 GB/s**，Base64 编码 21 GB/s 以上，TLS 记录层加密 1.7 GB/s。

jpssl 是一个 C++20 的高性能跨平台密码学库（目前 v1.1.0），零依赖、自带 TLS 1.2/1.3、DTLS、QUIC 和国密 SM2/SM3/SM4。仓库地址：[https://github.com/DaChengTechnology/JPSSL](https://github.com/DaChengTechnology/JPSSL)

> 以下数字全部来自项目自带的基准程序和 README/CHANGELOG 实测记录（i7-13700K / Raptor Lake、MSVC Release），文末有复现方法，欢迎自己跑。

## 先看成绩单

|---|---|---|
| AES-128-GCM 解密（16 KiB 记录） | **约 7 GB/s** | 反超 OpenSSL 约 1.6× |
| AES-128-GCM 加密（16 KiB 记录） | 约 3.8 GB/s | 修复前仅 0.012 GB/s（约 300×） |
| AES-256-GCM 解密 | 约 3.9 GB/s | 反超 OpenSSL 约 1.3× |
| AES-128/256-GCM 加密（VAES 路径） | 约 3.8–4.2 GB/s | 瓶颈从 GHASH 拉回 AES |
| TLS 1.3 记录层加密（AES-128-GCM） | 约 1.7 GB/s | 单条 16 KiB 记录封装仅 0.7–1.1 µs |
| AES-128-CCM / CCM-8 加解密 | 1.9–2.4 GB/s | 解密反超 OpenSSL 1.16–1.46× |
| Base64 编码 / 解码（AVX2 自动分派） | 21–22 / 17 GB/s | 标量只有 3 / 0.2 GB/s |
| SHA-1 批量哈希（AVX2 8 路） | 约 2147 MiB/s | 标量 597 MiB/s，约 3.6× |
| SM3 | 约 390 MB/s（MSVC 汇编） | 与 OpenSSL 持平 |
| SM4 ECB / GCM | — | 反超 OpenSSL 约 1.2–1.3× |
| SM2 签名 / 验签 | 约 105 µs/op | 反超 OpenSSL 约 1.35× / 1.26× |
| Ed25519 批量验签（256 条） | 10.5–12 ms | 反超 OpenSSL 逐条约 2.3–2.6× |

| X25519 ECDH | 39.6 µs/op | 约 1.15× OpenSSL EVP |
| RSA-2048/4096 CRT 解密 | — | 半尺寸汇编 + OpenMP 双线程提速 1.5–1.7× |

注意几个细节：AES-GCM 的 7 GB/s 不是"整块大 buffer 刷分"，而是按 **16 KiB TLS 记录分片、逐记录派生 nonce** 的真实记录层场景；Base64 的 21 GB/s 跑在 i7-13700K（没有 AVX-512）上，靠的是 AVX2 路径。

## 吞吐是怎么抠出来的

**1. SIMD 多路并行，一路怼到底**

AES-GCM 有 AVX2 4 路并行、AVX-512 8 路并行，以及专门给 Alder Lake / Raptor Lake 这类"熔断 AVX-512 但仍支持 256-bit VAES"的 CPU 准备的 VAES 后端（一条 `vaesenc` 处理 2 个 AES 块）。ARM 侧是 AESE + PMULL 的 4 块并行。

真正难啃的是 GHASH——GCM 的认证部分，算不好整个吞吐都被它拖死。项目把 GHASH 改成寄存器内 PCLMULQDQ 乘法 + 4/8 路并行，又引入 256-bit VPCLMULQDQ 一次算两个独立的 128-bit 无进位乘法，才把瓶颈从 GHASH 拉回 AES 本身。

**2. 零拷贝记录层**

TLS 加密一条 16 KiB 记录，业界常见的写法会经过"明文 → 中间 vector → 密文"多次搬运。jpssl 的记录层直接就地加密：记录头、inner 帧、标签占位一次构建，密文写回原缓冲，**每条记录只剩一次不可避免的明文写入**，单记录封装开销降到 0.7–1.1 µs。

**3. 批量吞吐，摊薄单次成本**

- Ed25519 批量验签改成随机盲化的多标量乘法：256 条签名共享同一条 4-bit 窗口倍点链，批量 10.5–12 ms，单条摊销 41–47 µs，而单条验证约 100 µs；
- ECDH 批量求逆摊薄成本：P-256 提升 1.20×、P-384 提升 1.27×，P-384 批量直接反超 OpenSSL；
- SHA-1 多缓冲：8 路（AVX2）/ 16 路（AVX-512）等长消息同时算。

**4. 汇编级优化**

RSA 的 CIOS Montgomery 乘法在 Windows 走手写 MASM（MULX 加速）、Linux 走内联汇编；CRT 解密再叠加"半尺寸模幂"（只算前 K/2 个 limb）+ OpenMP 双线程并行两条模幂，2048/4096 解密实测提速 1.5–1.7×。SM2 域运算也有 ADX 汇编路径，相对纯 C 实现约 2.0–2.2×。

**5. 运行时自动分派，老 CPU 不崩**

所有 SIMD 路径按 CPUID / HWCAP 在运行时选择：AVX-512 > VAES > AVX2 > 标量，ARM 上 SHA-512/SHA-3/SM3/SM4 这些 v8.4+ 可选扩展用原生指令（`vsha512hq2`、`vsm3*`、`vsm4e`），不支持的 CPU 自动回退标量，不会触发非法指令。这意味着性能优化不会变成兼容性噩梦。

## 吞吐没有牺牲平台覆盖

- **Windows / MSVC x64**：MASM 汇编 + `__cpuidex` 运行时检测，硬件加速全量生效；
- **Android arm64-v8a**：NEON/crypto 全量启用，JNI 导出 + Kotlin 扩展函数；
- **iOS 13+**：纯 arm64，NEON 加速，Swift Package + XCFramework；
- **鸿蒙 HarmonyOS NEXT / OpenHarmony 7.0+**：专用 toolchain，arm64 下 NEON 全量；
- **Linux**：同源码另有实验性 MUSA GPU 加速（ChaCha20 GPU 1.1 GB/s vs CPU 0.5 GB/s）。

## 和 OpenSSL 同台对比，不吹全面碾压

库本身**零依赖**——随机数、证书、TLS 全部自研，OpenSSL 只出现在基准的对比栏里。对比结果里有持平的（CCM 与 OpenSSL 持平、SM3 持平），也有确实反超的：

- AES-128-GCM 解密反超约 1.6×，AES-256-GCM 解密反超约 1.3×；
- SM2 keygen / sign / verify 反超 1.31× / 1.35× / 1.26×；
- Ed448 keygen / sign / verify 达到 5.7× / 6× / 2.3×；
- X25519 ECDH 约 1.15×。

再加上 TLS 1.2/1.3 与 OpenSSL 4.0 双向互通、DTLS 1.2/1.3 与 wolfSSL 5.9.2 八项全过——"自研"和"互通"并不矛盾。

## 吞吐自己跑一遍

```bash
git clone https://github.com/DaChengTechnology/JPSSL.git
cd JPSSL
cmake -B build -DCMAKE_BUILD_TYPE=Release -DJP_ENABLE_BENCH=ON
cmake --build build --config Release

# 密码套件吞吐（16 KiB TLS 记录、逐记录 nonce，最接近真实场景）
./build/benchmarks/bench_cipher_suites --data-mb 32 --record 16384 --rounds 5

# Base64 标量 vs AVX2 vs AVX-512 vs 自动分派
./build/benchmarks/bench_base64

# SM4、SM2/SM3、Ed25519、X25519、RSA…… 对应的 bench_* 目标都在 benchmarks/ 下
```

## 适合谁

- **高吞吐场景**：网关、代理、CDN 边缘、大数据加密管道，先把吞吐数字摆出来再谈；
- **信创/国产化**：国密 SM2/SM3/SM4 + RFC 8998 TLS 1.3 国密套件，性能还反超 OpenSSL；
- **多端团队**：同一份 C++ 源码出 Windows / Android / iOS / 鸿蒙库，各平台都吃到硬件加速；
- **被 OpenSSL ABI 坑过的人**：零依赖，没有版本地狱；
- **想学高性能密码学实现的人**：SIMD、汇编、批量算法全在源码里，基准和互通用例都是现成教材。
