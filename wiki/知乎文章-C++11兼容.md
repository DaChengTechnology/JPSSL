# 应评论区要求，jpssl 现在支持 C++11 了

前两篇聊了 jpssl 的吞吐量、测试与互通方法论，评论区出现频率最高的一个请求是：

> 我们项目还锁在 C++11，能降级吗？

这个诉求非常现实：存量代码、老工具链、嵌入式 / 车机 / 工控场景，很多至今还是 C++11。之前没敢直接答应，因为库里确实用了 C++20 的 `span`、`consteval` 和协程。这周我们把这件事做完了：**jpssl 已支持 C++11+（GCC/Clang），MSVC 最低 C++14**，代码在 `codex/cpp11` 分支：

[https://github.com/DaChengTechnology/JPSSL/tree/codex/cpp11](https://github.com/DaChengTechnology/JPSSL/tree/codex/cpp11)

## 为什么降级没有想象中难

jpssl 虽然标称 C++20，但真正依赖 C++20 语法的部分其实只有三处：

1. `std::span`（大量 API 的缓冲区视图）；
2. `consteval`（AES 表等编译期求值）；
3. 协程 I/O（`co_send` / `co_recv`，可选功能）。

算法内核——SIMD 与内联汇编、Montgomery、TLS / DTLS / QUIC 状态机、国密 SM2/SM3/SM4——本来就是"C++11 能写的代码 + 平台汇编"，不存在语法障碍。所以改造思路不是重写，而是：**把 C++20 专属特性做成兼容层，把可选特性条件编译**。

## 具体改了什么

**1. 三个"零开销"兼容头**

| 头文件 | 高版本行为 | 低版本行为 |
|---|---|---|
| `include/jpssl_span.hpp` | C++20 直接 `using span = std::span` | C++17 及以下自实现 `jpssl::span`（data/size/empty/[]/subspan/first/last、指针+长度/数组/std::array/容器构造、静态 extent） |
| `include/jpssl_optional.hpp` | C++17 起复用 `std::optional` | C++14/11 自实现（nullopt / 构造赋值 / 观察器 / emplace / make_optional） |
| `include/jpssl_memory.hpp` | C++14 起复用 `std::make_unique` | C++11 自实现行为等价的 `jpssl::make_unique` |

这样在高版本编译器下，兼容层只是别名，零额外开销、零行为差异；只有低版本下才走真实实现。

**2. 语法降级**

- `consteval` → `constexpr`；
- `inline constexpr` → `constexpr`（命名空间级常量，C++14 头文件安全）；
- `if constexpr` → 编译期 tag dispatch（rsa.cpp）/ 普通 if（sm3_neon.cpp，两分支均合法）；
- `std::clamp` → 手写 min/max。

**3. 协程 I/O 条件编译**

`co_send` / `co_recv`、`tls_co_executor` 整套协程 API 按 `JPSSL_HAS_COROUTINE` 保护：C++20 下原样可用，C++17 及以下自动禁用（头文件、源码、测试、示例一起关闭）。非阻塞事件循环、外部 fd 托管、UDP 数据报模式这些非协程 API 不受影响。

**4. 一个很关键的细节：判断标准改用语言版本宏**

兼容头里判断"该用标准库还是自实现"，用的是 `_MSVC_LANG` / `__cplusplus`，而不是特性测试宏。原因是 MSVC 在低标准模式下也会定义 `__cpp_lib_make_unique`，用特性测试宏会把 `std::make_unique` 错误地引入 C++11 代码。这类工具链怪癖，只有真的拿旧标准编一遍才能发现。

**5. 构建系统**

CMake 默认标准从 C++20 降为 C++17（根工程、Android、MUSA 同步），并允许显式覆盖：

```bash
cmake -S . -B build -DCMAKE_CXX_STANDARD=11 -DCMAKE_BUILD_TYPE=Release
```

## 验证结果

- 分支提交记录：**MSVC 全量构建 + ctest 37/37 全部通过**，C++14 / C++17 / C++20 回归正常；
- README 已更新为 "C++11+ 高性能密码学库（CPU + MUSA GPU，MSVC 最低 C++14）"；
- 写这篇文章前，我又把三个兼容头抽出来在 MSVC 下做了冒烟编译：C++14 模式走自实现路径、C++20 模式走标准库别名路径，两种路径编译运行都通过。

一个需要如实说明的点：**MSVC 没有 `/std:c++11` 开关，默认语言模式就是 C++14**。所以严格的表述是：GCC / Clang 最低 C++11，MSVC 从 C++14 起；MSVC 的默认构建走的正是 C++11 兼容实现路径。

## 怎么用

```bash
git clone -b codex/cpp11 https://github.com/DaChengTechnology/JPSSL.git
cd JPSSL
cmake -S . -B build -DCMAKE_CXX_STANDARD=11 -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
```

- **GCC / Clang**：`-DCMAKE_CXX_STANDARD=11` 即可全量构建 + 测试；
- **MSVC**：不用指定 C++11（本来就不支持该开关），默认 C++14 构建即是兼容路径；
- **协程 I/O 示例**（`coroutine_echo`）仍要求 C++20，其余所有功能——TLS 1.2/1.3、DTLS 1.2/1.3、QUIC v1/v2、国密 SM2/SM3/SM4、X.509、全部算法——在 C++11 下完整可用。

另外分支里还顺带新增了 **TLS 1.3 + RSA-2048 新建连接速率基准**，并修复了"真正 C++14 构建"（不是只改 CMake 标准号那种假兼容）。
